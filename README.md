# Классификация тональности отзывов Кинопоиска

Сервис определяет тональность русскоязычного отзыва (**Bad / Neutral / Good**), чтобы приоритизировать жалобы и отслеживать динамику удовлетворённости. Проект охватывает весь путь: честная валидация, сравнение подходов, трекинг экспериментов (MLflow), REST API (FastAPI), хранение предсказаний и аналитика (SQL), Docker, тесты и CI.

## Главные результаты

Основная модель сервиса: **ruBERT (`DeepPavlov/rubert-base-cased`), дообученный на отзывах Кинопоиска**, вход 256 токенов (начало и конец отзыва).

**Финальная оценка на test (6 212 отзывов, оценивалась один раз после выбора модели):**

| Модель | macro-F1 (95 % интервал) | F1 Bad | F1 Neutral | F1 Good |
|---|---|---|---|---|
| TF-IDF + логистическая регрессия | 0.681 (0.666-0.695) | 0.758 | 0.372 | 0.912 |
| **ruBERT-256, начало + конец** | **0.720 (0.707-0.734)** | 0.801 | 0.451 | 0.907 |

- Выигрыш трансформера над простой моделью составляет около +0.04 macro-F1 и заметен на редких классах (Neutral: +0.08, Bad: +0.04). На частом классе Good он отсутствует, а accuracy у моделей одинаковая (0.824 и 0.827).
- Класс **Neutral остаётся слабым местом** (F1 0.45): ruBERT находит 57 % нейтральных отзывов, но около 12 % хороших ошибочно называет нейтральными.
- Результат на test (0.720) согласуется с валидацией (0.726), то есть выбор модели по val не оказался подогнанным.

**Матрица ошибок ruBERT-256 на test (строки: истина, столбцы: ответ):**

| | Bad | Good | Neutral |
|---|---|---|---|
| Bad | 607 | 13 | 155 |
| Good | 34 | 4085 | 571 |
| Neutral | 99 | 219 | 429 |

## Данные и валидация

- Датасет [`blinoff/kinopoisk`](https://huggingface.co/datasets/blinoff/kinopoisk): 36 591 отзыв, Good 27 264, Bad 4 751, Neutral 4 576 (лицензия MIT). Классы сильно несбалансированы.
- Разбиение **по названию фильма** (отзывы одного фильма не попадают в разные части, это проверяет тест): train 25 281, val 5 098, test 6 212.
- Главная метрика **macro-F1**: accuracy здесь вводит в заблуждение (около 75 % отзывов Good, модель «всегда Good» получила бы такую accuracy).
- test использовался один раз, после выбора модели по val и gold-набору. Скрипт защищён от повторного запуска, результат лежит в `reports/final_test.json`.

## Что сравнивали

Результаты на val (5 098 отзывов), seed 42, по одному запуску:

| Запуск | macro-F1 | F1 Neutral |
|---|---|---|
| TF-IDF + LogReg (бейзлайн) | 0.656 | 0.343 |
| ruBERT, 256 токенов, только начало | 0.652 | 0.379 |
| **ruBERT, 256 токенов, начало + конец** | **0.726** | 0.476 |
| ruBERT, 512 токенов, начало + конец | 0.733 | 0.491 |

- **Как обрабатывать длинные отзывы:** 27 % отзывов длиннее 512 токенов, 67 % длиннее 256 (оценка по 3 000 отзывов train). Простая обрезка до начала дала качество на уровне TF-IDF (0.652 против 0.656), а стратегия «четверть бюджета с начала, остальное с конца» подняла macro-F1 на 0.07. Вероятное объяснение: вывод рецензента часто стоит в конце (мы это не проверяли напрямую).
- **Окно 512 против 256:** разница +0.007 при вдвое большем времени обучения (77 против 39 минут на двух T4). Статистически мы это не проверяли и считаем разницей в пределах возможного шума, поэтому в сервис пошла более быстрая модель на 256.
- Обучение: 3 эпохи, lr 2e-5, эффективный батч 32, fp16, взвешенная функция потерь по классам, лучшая эпоха выбиралась по macro-F1 на val. Обучение шло на Kaggle (2×T4).

**Качество в зависимости от длины отзыва (ruBERT-256 на val):**

| Слов в отзыве | Отзывов | macro-F1 | F1 Neutral |
|---|---|---|---|
| до 50 | 77 | 0.624 | 0.507 |
| 50-150 | 743 | 0.728 | 0.500 |
| 150-300 | 2 078 | 0.738 | 0.452 |
| 300-600 | 1 749 | 0.720 | 0.449 |
| от 600 | 451 | 0.683 | 0.378 |

Группы оценивались на выборке до 300 отзывов, а в первой группе всего 77 отзывов, поэтому метрики шумные. Заметно только снижение качества на самых длинных отзывах.

## Проверка на другом домене и LLM-бейзлайн

Чтобы понять, как модель переносится за пределы кино, **вручную размечен gold-набор из 202 отзывов на товары** (датасет `ai-forever/ru-reviews-classification`, тестовая часть; 210 отобрано, 8 пропущено). Разметка выполнена одним человеком по письменной инструкции (`src/review_sentiment/annotate.py`). Согласие с метками датасета: 70 %, каппа Коэна 0.55.

Третий подход: открытая LLM **Qwen2.5-7B-Instruct** без дообучения, few-shot промпт (6 примеров Кинопоиска, версия `v1`), ответ в JSON с проверкой через pydantic. Все модели оценены на одних и тех же отзывах, интервалы получены бутстрепом, разницы между моделями парным бутстрепом (`src/review_sentiment/compare_llm.py`).

| Выборка | TF-IDF | ruBERT-256 | LLM Qwen2.5-7B |
|---|---|---|---|
| val Кинопоиска, 500 отзывов | 0.583 | 0.722 | 0.745 |
| gold, товары, 202 отзыва | 0.389 | 0.411 | **0.724** |

- **На Кинопоиске LLM и ruBERT не различаются статистически:** разница +0.022, интервал −0.028…+0.078.
- **На товарах ruBERT, обученный на кино, резко теряет качество** и почти не распознаёт позитив (F1 по Good 0.08; большинство хороших отзывов он называет нейтральными). LLM обгоняет его на +0.31 (интервал +0.22…+0.39).
- LLM вернула корректный JSON во всех 702 запросах (500 val и 202 gold).

**Стоимость:**

| | TF-IDF | ruBERT-256 | LLM Qwen2.5-7B |
|---|---|---|---|
| Размер модели | не измеряли | около 0.7 ГБ | около 15 ГБ |
| Скорость | не измеряли | 0.25 с на отзыв (медиана), CPU, по одному | 2.3 с на отзыв, 2×T4, пачки по 8 |

Скорости получены в разных условиях и не сопоставимы напрямую: у LLM указана пропускная способность на пачках, а не задержка одного запроса.

**Вывод по выбору модели:** на данных задачи (Кинопоиск) качество LLM и ruBERT одинаково, а ruBERT на порядок меньше и работает на обычном процессоре, поэтому в сервис пошёл он. Если бы нужны были отзывы на товары, выбор был бы обратным.

## Ограничения

- **Только домен «фильмы».** На отзывах на товары модель работает плохо (см. выше). Для другого домена нужна собственная разметка и дообучение; мы это не делали.
- **Neutral размыт.** Метки этого класса шумные: в gold-наборе разметчик отнёс к Bad 29 из 66 отзывов, которые датасет считает Neutral. Читать F1 по Neutral отдельно от остальных метрик нельзя.
- **Один запуск и один seed** на каждый вариант обучения. Интервалы показывают разброс по отзывам, а не по запускам.
- **gold-набор размечен одним человеком**, а определения классов в LLM-промпте совпадают с его инструкцией: часть преимущества LLM над ruBERT на gold может объясняться тем, что ruBERT этих определений не видел.
- **LLM не оценивалась на test** (6 212 отзывов по 2.3 с заняли бы около четырёх часов), только на выборке val и на gold-наборе. Оценена одна модель и один промпт.
- **Предупреждение о коротком тексте в API (порог 50 слов)** основано на малой выборке (77 отзывов) и считается ориентировочным.
- **Docker.** Образ собирается и проверяется в CI (GitHub Actions: сборка, импорт зависимостей, проверка синтаксиса `docker-compose.yml`). На машине автора Docker не установлен, поэтому запуск контейнеров и связки с PostgreSQL локально не проверялся.
- Модель лежит в **приватном** репозитории Hugging Face, поэтому для запуска сервиса нужен доступ к ней либо собственное обучение (инструкция ниже).

## Сервис

| Эндпоинт | Что делает |
|---|---|
| `GET /health` | статус сервиса, загружена ли модель |
| `POST /predict` | принимает `{"text": "..."}`, возвращает класс, вероятности и предупреждение для коротких текстов; сохраняет отзыв и предсказание в базу |
| `GET /stats/daily` | доля негативных отзывов по дням |
| `GET /stats/negative` | отзывы с наибольшей вероятностью класса Bad за последние дни |

Хранилище: SQLAlchemy, по умолчанию файл SQLite, а в `docker-compose.yml` PostgreSQL (переменная `DATABASE_URL`). Образ с сервисом весит 1.32 ГБ (PyTorch для процессора, веса подгружаются при старте). Пароль PostgreSQL в compose-файле демонстрационный: в реальной среде его нужно брать из секретов.

## Структура репозитория

```

  baseline.py        TF-IDF + логистическая регрессия

  predict.py         загрузка модели и предсказание

  token_stats.py     длина отзывов в токенах
  length_analysis.py качество по длине отзыва
  make_gold.py, annotate.py, evaluate_gold.py   gold-набор
  llm_baseline.py    LLM few-shot бейзлайн
  compare_llm.py     сравнение моделей на одних отзывах
  latency.py         замер задержки ruBERT
  final_test.py      финальная оценка на test (один раз)
```

## Как воспроизвести

Нужны Python 3.11 и [uv](https://docs.astral.sh/uv/).

```bash
uv sync
uv run python -m review_sentiment.data        # данные и разбиение
uv run python -m review_sentiment.baseline    # бейзлайн, запись в MLflow
uv run pytest -q                              # тесты
uv run mlflow ui --backend-store-uri sqlite:///mlflow.db   # таблица экспериментов
```

Дообучение ruBERT рассчитано на GPU (в проекте запускалось на Kaggle, 2×T4):

```bash
python -m review_sentiment.train --max-len 256 --strategy head_tail --run-name rubert-256-head_tail
```

Сервис (модель берётся из репозитория Hugging Face, переменные `MODEL_REPO` и `MODEL_SUBFOLDER` позволяют указать свою; для приватного репозитория нужен вход через `hf auth login` или переменная `HF_TOKEN`):

```bash
uv run uvicorn review_sentiment.api:app
```

Через Docker (не проверялось локально, см. ограничения):

```bash
HF_TOKEN=<токен> docker compose up --build
```
